## Novedades para el cliente

### Integración con Labcore
- **La Labcore API vuelve a correr dentro del servidor del LIS**, como un servicio más del
  stack. Deja de depender de la máquina Windows donde se la instaló en septiembre
  (192.168.5.14, servicio `LabcoreApi`): se actualiza con cada release junto con todo lo
  demás, y no vuelve a pasar que el pasaje de órdenes quede con una versión vieja de la API
  (lo del 2026-11-16: Usuario, Prioridad, Fecha de retiro y Diagnóstico vacíos).
- Si la orden del LIS trae resultados iniciales (valores cargados en la admisión), ahora
  viajan a Labcore junto con la orden.

Nada cambia en la operación: las órdenes siguen llegando a Labcore igual que antes, y la
búsqueda de pacientes en la admisión sigue consultando Labcore.

## Notas de deploy

- Sin migraciones nuevas.
- **Por qué ahora sí anda en Docker**: el SQL Server de Labcore (192.168.5.10) es 2008 R2 RTM y
  su Schannel no lee los registros TLS vacíos que OpenSSL manda antes de cada registro de datos
  en TLS 1.0 con cifrados CBC (contramedida contra BEAST). El handshake y el login salían bien y
  el driver se quedaba esperando la respuesta para siempre ("Connection Timeout Expired ...
  post-login phase"). La imagen de la API ahora apaga esa contramedida
  (`Options = -EmptyFragments` en `docker/openssl-legacy-sqlserver.cnf`, sólo para el TLS
  saliente de ese contenedor). Verificado antes del deploy contra la base real: la config vieja
  tardaba 15 s en fallar; con la nueva, `/health/ready`, la búsqueda de pacientes y el catálogo
  de estudios (400 KB) responden en menos de un segundo.
- `.env` del server: vuelve `LABCORE_LIS_CONNECTION_STRING` (la misma cadena de septiembre, con
  `Encrypt=True;TrustServerCertificate=True`) y `LABCORE_API_URL` queda comentada: el adapter
  usa el default `http://labcore-api:5080`. Backup en `.env.bak-*-labcore-docker`.
- Servicio nuevo `labcore-api` (contenedor `lis-labcore-api`), con volumen `labcore-api-logs`,
  `labcore-api/appsettings.Production.json` y `sql-overrides/` montados. El healthcheck mira
  `/health/live`; la base se mira con
  `docker exec lis-labcore-api curl -s http://localhost:5080/health/ready` → `Healthy`.
- `redeploy.sh` y `clone-repos.sh` vuelven a conocer el repo (`/opt/lis/labcore-api`, ya estaba
  clonado). `build-labcore-api-windows.ps1` queda como alternativa, no es el camino normal.
- **Pendiente en la máquina del cliente**: detener y deshabilitar el servicio de Windows
  `LabcoreApi` en 192.168.5.14 (`Stop-Service LabcoreApi; Set-Service LabcoreApi -StartupType Disabled`,
  o `uninstall-windows-service.ps1` del paquete). Ya nadie lo llama; apagarlo evita que dos
  instancias con versiones distintas escriban en la misma base.
